## Що перевірено окремо

- **Тести, типи:** `uv run pytest tests/unit/translation` → 1542 passed. `uv run mypy src/collector/translation` → Success. У `src/collector/translation` немає жодного `type: ignore`/`noqa`.
- **Segmenter, стійкість:** обхід ітеративний. 50k вкладених `<div>` → 0.46 с, 50k `<span>` → 0.58 с, 50k неявно закритих `<li>` → 0.71 с. `_IMPLIED_END_SCAN=256` обмежує пошук. 50k незакритих `<b>` з `max_segment_chars` → 0.63 с. Поділ на речення (50k речень) → 0.31 с. Числові regex (`_AMOUNT_RE`, `_BARE_NUMBER_RE`, `_DATE_RE`) на патологічних рядках (`1,1,1…`, `1.111…`, 50k цифр, `11/11/…`) — усі < 0.2 с: lookbehind не дає стартувати всередині числа. `_URL_RE` має якір на літералі.
- **Маскування і колізії:** літеральний текст `<x id="1"/>` у джерелі після `unescape` → `html.escape` стає `&lt;x…&gt;` і з placeholder-ом не колізує. Невідомий тег `<x>` як розмітка стає блочним і в сегмент не потрапляє. Noncharacters U+FDD0/U+FDD1 у вході замінюються на U+FFFD лише коли ввімкнено атрибути; заміна втрачає дані, але задокументована.
- **TM key:** рівно 5 компонентів (provider — пара `name`/`model_version`), `canonical_json_bytes` (`sort_keys`, `ensure_ascii=False`, `separators`) детермінований між версіями Python. Хеш сегмента залежить від `unicodedata` (NFC + категорії Cc/Cf), тобто від версії Unicode інтерпретатора. `requires-python = ">=3.13,<3.14"` фіксує її. Під час переходу на 3.14 зміна можлива лише для символів, які в Unicode 15.1 були непризначені: практично нуль, але це варто враховувати як потенційну інвалідацію TM. Хеш рахується з masked-тексту: сегменти, що відрізняються лише числами/URL/тегами, ділять один запис TM за задумом (О-2). Переклад TM-хіта теж проходить `validate_preservation`.
- **Pipeline:** дедуплікація за key, порядок `zip(batch, results, strict=True)` коректний. Неповна відповідь → `provider_truncated`, `complete=False`. Валідні нові переклади пишуться в TM навіть при частковому провалі (first-write-wins). Для атрибутів `unescape` → `escape` симетричні.
- **Детектор:** `lru_cache(maxsize=4)` на `frozenset` — кеш на процес. За одночасного першого виклику з двох потоків детектор може побудуватись двічі: це зайва пам'ять, коректність не страждає. Lingua (Rust) детермінований, тест між процесами є. Моделі вантажаться ліниво за мовою. Невідомий для lingua код в extra-мовах дає `ValueError` під час побудови, тобто fail-fast.
- **Локальні типи з TODO (WP-01C PR2):** `QualityFlag` — `Literal` з тими самими значеннями. Якщо WP-01C оголосить `TranslationQualityFlag` як `StrEnum` (як `TranslationStatus`), mypy вимагатиме замінити рядкові літерали приблизно в 6 місцях (`planner.py`, `pipeline.py`). Під час виконання `StrEnum == str`, тож механічна заміна безболісна. `ArticleText` — плоский dataclass, мапінг з `NewsVersionCreatedEvent` буде тривіальним.
- **Залежність `lingua-language-detector` 2.2.0 (факти):** wheel ≈ 170 МБ на всіх платформах. У lock лише `cp313`-wheels, sdist немає, тож перехід на Python 3.14 заблоковано до виходу cp314-wheels. +45 МБ RSS на 19 мов (вимір тестувальника). Альтернативи: `py3langid` (numpy + модель кількох МБ, детермінований, слабший на коротких сегментах); `langdetect` (pure Python, ~1 МБ, недетермінований без `DetectorFactory.seed`, повільніший); fastText `lid.176.ftz` (~1 МБ модель, але пакет `fasttext` погано підтримується і має проблеми з wheel-ами). Low-accuracy режим lingua зменшує RSS, але не розмір wheel. Рішення — не за рев'ю.
- **Безпека:** мережевого I/O немає. `yaml.safe_load`. `html.parser` не розкриває entity/DTD (XXE неможливий). Секретів і контактів у логах немає, бо логування відсутнє.
