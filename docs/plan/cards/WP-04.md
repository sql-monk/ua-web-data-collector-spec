## Scope

Ядро перекладу новин українською (§10 кроки 11–12): HTML-безпечний segmenter і reassembly, визначення мови по сегментах, translation memory з ключем FR-017, versioned glossary, маскування і перевірка preservation (числа, дати, URL, e-mail, імена/терміни glossary), provider interface з Google Cloud Translation Advanced adapter (online), character budget із пріоритетами title/lead → body нової статті → backfill, `TranslationHandler` для ролі `translation` runtime-у WP-01D, збирання immutable translation version з TM, метрики-лічильники §14.1 і golden multilingual corpus для 16 вихідних мов із offline QA-прогоном.

Модель мов (з §1 п.2, §8 і `docs/research/**`, файли research не змінюються): 19 країн; 16 вихідних мов `de, fr, en, lt, lv, et, pl, hu, ro, cs, sk, sl, hr, it, es, nl`; `uk` — цільова і водночас мова UA-джерел (`not_required`). Мова визначається по статті й по сегменту, а не за країною: BE дає `nl`/`fr`/`de` (і `en` у Brussels Times), RO-джерела мають HU/EN секції, LSM — кілька мовних sitemap.

## Out of scope

- Виділення тексту з HTML сторінки, parser order, `content_access` конкретного item — WP-05/WP-06x (WP-04 отримує вже cleaned HTML/текст і `content_access`).
- Схема PostgreSQL, міграції, GRANT — WP-01A (лише dependency-запити); Pydantic-контракти і JSON Schema — WP-01C.
- Worker runtime (claim/lease/drain), compose-сервіс `translation-worker` — WP-01D; секрети в `deploy/**` — WP-00.
- Read API перекладів — WP-11A; експорт метрик, алерти, capacity snapshot — WP-12.
- Локальний NLLB/Marian provider: лише інтерфейс, який його допускає; реалізація — після benchmark і ADR (§8).
- Google Cloud **batch** translation (потребує GCS bucket і окремої інфраструктури) — див. «Відкрите для оркестратора» О-6.
- Redis TM hot cache (§8, optional) — не в MVP; PostgreSQL — source of truth.
- Human QA 30 перекладів на мову — виконують люди поза агентами (§7 плану, рівень 7); WP-04 дає інструмент, шаблон rubric і формат `translation_quality_result`.
- Живі виклики Google API у тестах і CI; будь-який live-прогін — лише з дозволу користувача (§11 плану, п. (г) — зовнішні витрати).

## Відкрите для оркестратора

- **О-1. Де зберігати бюджет.** §9.1 не містить таблиці бюджету перекладу. Варіанти: (а) **рекомендовано** — нова таблиця у WP-01A PR3 (`translation_budget_periods`: period, budget class `fresh|backfill`, limit/reserved/consumed chars, revision) з row-lock reserve за патерном `origin_rate_buckets`; (б) без нової таблиці — `SUM(character_count)` з `news_translations` за період під `pg_advisory_xact_lock`: без reservation, допускає перевитрату на розмір одного batch-а. Mongo не підходить (news/translations за §7/§9.1 живуть у PostgreSQL).
- **О-2. Де живе функція TM key.** Рекомендовано в `collector.translation.memory` (споживач — WP-04 і колонка WP-01A, що зберігає готовий hex); якщо WP-11A/WP-12 знадобиться обчислювати ключ — перенести в `contracts/identity.py` через WP-01C.
- **О-3. Хто ставить translation jobs.** `collector_translation` не має INSERT на `crawl_jobs`. Варіанти: (а) **рекомендовано** — в тій самій транзакції, що `upsert_article_version` (WP-01A PR3 repo, викликач WP-05), через чисту функцію WP-04 `plan_translation_jobs(version_meta) -> list[NewJob]`; (б) споживач outbox `news.version_created` під роллю scheduler (publisher — WP-01B). WP-04 у PR2 дає planner у будь-якому варіанті.
- **О-4. Гранулярність jobs і збирання version.** Рекомендовано: два job-и на article version — `translation.head` (title/lead, priority 300) і `translation.body` (priority 200; не створюється, якщо body відсутній — R-20), backfill-версії — `translation.backfill` (priority 100, `args.backfill=true`). Кожен job перекладає свої сегменти в TM; immutable `news_translations` записує той job, який бачить повний набір сегментів у TM, через `INSERT … ON CONFLICT DO NOTHING` за `translation_idempotency_key` — рівно одна version без гонки. Альтернатива (один job на version) простіша, але не дає глобального пріоритету title/lead над body інших статей (§15).
- **О-5. Мови поза 16.** Сегменти `ru`, `ca` тощо (Baltic/ES/RO джерела): рекомендовано перекладати, якщо provider підтримує, з quality flag `language_outside_golden_corpus` і без QA-гейта; альтернатива — `translation_failed` із retry plan.
- **О-6. Batch translation для backfill** (§8 «batch для backfill»): потребує GCS; рекомендовано відкласти окремим PR після pilot, у PR2 — online `translateText` з батчуванням сегментів у запиті.
- **О-7. Зберігання `translation_quality_result`** (§12.3): таблиці в §9.1 немає; рекомендовано `quality_results` WP-01A PR3 з типом `translation_rubric` або файл-звіт у `docs/plan/reports/<WP>/translation-qa.md` до появи API.

## PR1 — `wp/04-1-segmenter-tm`: segmenter, мова, TM, glossary, preservation

### Вимоги

1. **Segmenter (§10 крок 11, §16.1 п.1):** cleaned HTML → впорядкований список сегментів по блочних елементах (`p`, `li`, `h1–h6`, `blockquote`, `figcaption`, `td/th`, `dt/dd`), з поділом довгих блоків на речення лише за лімітом довжини запиту провайдера; inline-розмітка (`a`, `em`, `strong`, `b`, `i`, `br`, `span`, `sup/sub`) лишається всередині сегмента як захищені теги; `code`, `pre`, `script`, `style`, атрибути (`href`, `src`, `alt` — окремо як сегмент лише для `alt`/`title`, за конфігом) не перекладаються. `reassemble(segments, translations)` відновлює дерево. Парсер HTML — без мережі й без resolve зовнішніх entities (§13).
2. **Нормалізація для хешу (§12.2):** Unicode NFC, згортання пробілів і керівних символів; оригінальний текст не змінюється.
3. **Мова по сегментах (§5.4, §8, §12.2, R-08):** порядок — source-declared metadata → `lang` атрибут → classifier (`lingua-language-detector`, обмежений 17 мовами `uk` + 16 + конфіг О-5); короткі сегменти (< конфігурованого порогу) успадковують мову статті; результат із confidence; невпевненість зберігається, а не ігнорується.
4. **`not_required` (§5.4):** `original_language == uk` і жоден сегмент не визначено як не-`uk` → план без запитів до провайдера, status `not_required`, текст не дублюється. Змішана сторінка: не-`uk` сегменти перекладаються, `uk`-сегменти проходять як є.
5. **TM key (FR-017) — рівно 5 компонентів:** `source_language`, `target_language`, `normalized_segment_hash` (SHA-256 нормалізованого тексту з маскованими placeholder-ами), `provider/model` (пара `provider`, `model_version`), `glossary_version`; ключ — SHA-256 canonical JSON (використати `canonical_json_bytes`/`sha256_hex` з `collector.contracts`). Порт `TranslationMemoryStore` (`get_many(keys)`, `put_many(entries)`) + in-memory реалізація; PostgreSQL-реалізація — PR2.
6. **Glossary:** versioned файл(и) у `src/collector/translation/glossary/` (терміни/імена per language pair → українська форма або do-not-translate); `glossary_version` = SHA-256 canonical вмісту; застосування через маскування до запиту і підстановку після.
7. **Маскування і preservation (§10 крок 12, §12.1):** числа (з локальними форматами `1.234,5` / `1 234,5` / `1,234.5`), дати, відсотки, валюти, URL, e-mail, терміни glossary → placeholders до запиту; після — `validate_preservation(source, translated)`: 100% placeholders на місці, множина чисел збігається після нормалізації формату, URL побайтово ті самі, теги inline-розмітки збігаються за мультимножиною. Провал → сегмент з quality flag і відмова збирати version з цим сегментом (не «тихий» пропуск).
8. **План перекладу (R-20, FR-016):** `plan_article_translation(article)` → поля до перекладу за `content_access`: `metadata_only`/`blocked`/`challenge`/`premium`/`gone` — лише наявні title/lead; `full`/`partial` — плюс body, якщо він є; `body is None` → жодного body-сегмента і жодного згенерованого тексту.
9. **Q-009:** для нової article version з частково зміненим текстом до провайдера йдуть лише сегменти без TM hit; повна version збирається з TM + нових перекладів.

### Тести (unit, без мережі)

- segmenter: для кожного fixture з `tests/fixtures/translation/html/` `reassemble(segments, identity)` дає DOM, еквівалентний вхідному (порівняння нормалізованого дерева, не рядків); вкладені `a>strong`, `li` з `br`, `blockquote>p`, таблиця — теги не рвуться і не губляться; `code/pre/script` не стають сегментами; атрибут `href` незмінний; hostile HTML (незакриті теги, `<!ENTITY>`, дуже глибока вкладеність) не падає і не виконує resolve entities.
- TM key: зміна кожного з 5 компонентів окремо (`source_language`, `target_language`, текст, `provider`, `model_version`, `glossary_version`) → інший ключ (параметризований тест, 6 випадків, бо компонент 4 — пара); зміна лише пробілів/NFC-форми → той самий ключ; golden-значення ключа зафіксовано у fixture (стабільність між процесами/ОС).
- `uk`: стаття `uk` без іншомовних сегментів → `not_required`, провайдер-fake не викликано жодного разу, текст у sink не записано.
- змішані мови: стаття `uk` з цитатою `en` і абзацом `pl` → перекладено рівно 2 сегменти з правильними `source_language`; стаття `de` з `uk`-цитатою → `uk`-сегмент не надіслано; короткий сегмент (`«Так»`) успадковує мову статті.
- body nullable (R-20): `metadata_only` з title/lead → план без body; `full` з `body=None` → без body і без помилки; жоден шлях не створює body-текст.
- preservation 100%: набір кейсів (числа в трьох локальних форматах, дати, `%`, `€`/`zł`/`Ft`, URL з query, e-mail, ім'я з glossary) — fake-провайдер, що повертає коректний результат, проходить; fake, що змінює одну цифру / губить URL / переставляє placeholder / губить `</a>` — кожен ловиться валідатором (окремий тест на кожну мутацію).
- glossary: зміна одного терміна → новий `glossary_version` → новий TM key; do-not-translate термін доходить до результату незмінним.
- Q-009: v1 з 5 абзаців перекладено; v2 змінює 1 абзац → провайдер-fake отримав рівно 1 сегмент, зібрана v2 містить 5 перекладених абзаців.
- ідемпотентність: повторний переклад тієї самої version з тим самим provider/model/glossary → 100% TM hit, 0 викликів провайдера.

## PR2 — `wp/04-2-provider-budget`: provider interface, Google adapter, budget, handler

### Вимоги

1. **`TranslationProvider` (Protocol):** `name`, `model_version`, `max_request_chars`, `async translate(segments, source_language, target_language, mime_type) -> list[ProviderResult]`; помилки класифіковані: `ProviderRetryable` (429/5xx/timeout, з `retry_after`), `ProviderPermanent` (400 unsupported language, невалідний запит), `ProviderAuthError` (401/403 — не ретраїться нескінченно, як §10 крок 6). Інтерфейс допускає майбутній NLLB/Marian без зміни handler-а; результати різних provider/model не змішуються (провайдер/модель — у TM key і version).
2. **`GoogleTranslationProvider`:** REST v3 `projects/{project}/locations/{location}:translateText` через `httpx.AsyncClient` (тестується respx); `mimeType=text/html` для сегментів з inline-розміткою; батчування сегментів у межах ліміту запиту; timeouts за §10 (connect 10 с / read 30 с / total 60 с); токен — через порт `AccessTokenProvider` (продакшн-реалізація на `google-auth` service account, виконується поза event loop), у тестах — fake. Credentials — лише з файлу секрету за `COLLECTOR_TRANSLATION_CREDENTIALS_FILE` (§13, FR-013); у логах/помилках — ні токена, ні вмісту ключа (перевіряється разом із `redact()` runtime-у).
3. **Budget (§15, Q-008, R-09):** два класи — `fresh` (head і body нових статей) і `backfill`; `reserve(chars, class)` перед викликом провайдера, `commit(actual)` після, `release` при помилці; рахуються символи фактично надісланого payload (консервативно, включно з розміткою). Порядок: `translation.head` → `translation.body` → `translation.backfill` через `priority` черги (`claim` сортує `priority DESC`, `repositories/queue.py`). Default: `fresh` — ліміт з конфігу; `backfill` **paused без явного ліміту** (не налаштовано → жодного виклику провайдера для backfill). Вичерпання → deferral job-и до початку наступного періоду без спалювання спроб (dependency п.3а), status не `translation_failed`.
4. **`TranslationHandler`:** `job_types = ("translation.head", "translation.body", "translation.backfill")` (остаточно — за О-4); читає article version через порт, будує план (PR1), бере TM hits, reserve budget, перекладає miss-сегменти, валідує preservation, пише сегменти в TM, за наявності повного набору — immutable translation version під `translation_idempotency_key` (`ON CONFLICT DO NOTHING`). `ProviderRetryable` → `TaskResult.retryable`; `ProviderPermanent`/провал preservation після повтору → `translation_failed` + quality flags + `TaskResult.permanent` (з retry plan у `error_code`); `ProviderAuthError` → permanent з кодом `provider_auth`.
5. **Provider disabled (dev/CI без credentials):** `COLLECTOR_TRANSLATION_PROVIDER=disabled` (default у compose до появи секрету) → фабрика повертає `NoopHandler(role)`, який claim-ить лише `job_type == "translation"`, тож translation jobs лишаються `pending` з незмінним `attempt`; instance `ready`, стек `up --wait` не ламається (§16.3: відсутність credentials не ламає інші компоненти).
6. **Планувальник jobs:** чиста функція `plan_translation_jobs(version_meta) -> list[NewJob]` з idempotency key на базі `translation_idempotency_key` + частина (`head`/`body`); викликач — за О-3.
7. **PostgreSQL-адаптери портів** (`TranslationMemoryStore`, `BudgetLedger`, `TranslationSink`) — лише через репозиторії WP-01A PR3; жодного сирого SQL у `collector.translation` (правило WP-01A «Repository API»).
8. Реєстрація фабрики в `HANDLER_FACTORIES[WorkerRole.TRANSLATION]` за механізмом із dependency п.3б.

### Тести

- Unit, provider (respx, `pytest-socket` активний): успіх → переклад і коректний порядок сегментів; 429 з `Retry-After` → `ProviderRetryable(retry_after=…)`; 5xx/timeout → retryable; 400 → permanent; 401/403 → `ProviderAuthError`; невалідний JSON/менше перекладів, ніж сегментів → permanent, а не часткове збирання; батчування: 3 000 сегментів → кількість запитів відповідає ліміту, жоден запит не перевищує `max_request_chars`; без respx-маршруту → швидка помилка мережевої політики (Linux-паритет).
- Секрети: fixtures і тестовий код не містять `private_key`, `"type": "service_account"`, `ya29.`, `AIza` (скан `tests/fixtures/translation/**`); лог і `TaskResult.error_message` при `ProviderAuthError` не містять токена (caplog + перевірка рядка).
- Budget: ліміт 1 000 символів, 3 статті → head усіх трьох перекладено раніше за body будь-якої (порядок викликів fake-провайдера при спільній черзі); вичерпання посеред body → job deferred, `attempt` не змінився, TM зберігає вже перекладені сегменти, повтор після нового періоду добирає лише решту; backfill без налаштованого ліміту → 0 викликів провайдера, jobs deferred, а не failed; backfill із лімітом не використовує `fresh`-бюджет; паралельні `reserve` двох handler-ів не перевищують ліміт (integration на PostgreSQL за О-1 (а); за варіантом (б) — тест документує межу перевитрати).
- Ідемпотентність: повторний handle тієї самої job-и після успіху → 0 викликів провайдера (TM hit), рівно одна translation version; head і body, завершені паралельно, → рівно одна version (integration).
- `uk` → handler записує `not_required` без виклику провайдера й без reserve budget; `metadata_only` → лише head job, version без body.
- Preservation-провал від провайдера → `translation_failed` з quality flag, version з пошкодженим сегментом не записана.
- Provider disabled → після enqueue jobs лишаються `pending`, `attempt = 0`, instance `ready` (integration зі scaling-фікстурами WP-01D або unit на фабриці + runtime з fake queue).
- Integration (`tests/integration/translation/`, маркер `integration`, PostgreSQL 18 як у `tests/integration/postgres`): операції handler-а під **LOGIN-роллю `collector_translation`** (зразок `tests/integration/postgres/test_role_logins.py`) — може читати article version, писати TM/version/budget; не може INSERT у `crawl_jobs`, не може писати `normalized_artifacts`.
- `test_no_silent_skip.py` покриває нові файли; integration-тести в CI не skip-аються через відсутність Docker там, де job обіцяє PostgreSQL (патерн `E2E_REQUIRED` з `tests/e2e/test_gui_runtime_contract.py`).

## PR3 — `wp/04-3-golden-corpus`: golden corpus 16 мов, QA-runner, rubric

### Вимоги

Режим `--provider google` — лише ручний, лише з дозволу користувача і з бюджетом (§11 плану п. (г)); у CI не запускається.
