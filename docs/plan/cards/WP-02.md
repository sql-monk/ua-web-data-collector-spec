## Scope

Спільний fetch layer §7.1: нормалізація URL/origin (FR-014), Route Guard (allow/deny + глобальний denylist), SSRF-захищений HTTP-клієнт із DNS-pinning і перевіркою кожного redirect hop, потокові ліміти body (20 МБ / sitemap 100 МБ після розпакування), conditional GET, класифікація відповідей у `fetch_outcome`/`content_access` і скінченна retry policy §10, інтеграція з глобальним origin limiter (permit перед кожним запитом, 429/`Retry-After` → `block_origin`), claimed/verified PUT raw artifact-ів у S3/MinIO з `claim_generation` fencing і orphan sweeper (R-33/R-38/R-41), versioned robots snapshot, доменний `FetchHandler` для ролі `fetch` у runtime WP-01D, окремий browser worker image з pinned Playwright для винятків §3 п.11.

## Out of scope

Discovery/sitemap/RSS parsing і XML (XXE) — WP-03; parser/normalized payload і parse worker handler — **WP-05** (O-6, рішення оркестратора; WP-02 дає лише generic uploader і умови D-2 1–2); планування jobs і створення origin buckets (`ensure_bucket` — роль `collector_scheduler`) — WP-03/scheduler; `OriginPermitClient` як runtime-компонент — WP-01D PR2; виклик sweeper-а за розкладом, дашборди/алерти — WP-12; source manifests (`sources/<source_id>/manifest.yaml`) — адаптерні WP; live smoke будь-якого джерела — лише `source-canary` з дозволу користувача (у цьому WP не виконується).

## PR1 — `wp/02-1-http-ssrf-limits`: URL/origin, Route Guard, SSRF-клієнт, ліміти, retry decisions, permits

### Вимоги

1. **URL (FR-014)** — `collector/fetch/urls.py`: `normalize_url(raw) -> NormalizedUrl` (lowercase scheme/host, IDNA, прибрати default port, fragment і tracking-параметри за `tracking_query_keys`; вихідний рядок зберігається) і `normalize_origin(url) -> str` (`scheme://host[:port]`) — **єдиний** ключ `origin_rate_buckets.origin`; WP-03/scheduler імпортують саме цю функцію.
2. **Route Guard** — лише `http`/`https`; дозволені порти за замовчуванням 80/443 (override з policy); allow/deny patterns + глобальний denylist (O-4); перевірка до кожного запиту і на кожному hop.
3. **SSRF (§13)** — `collector/fetch/ssrf.py`: резолв **усіх** A/AAAA; блок, якщо **хоча б одна** адреса не глобальна: loopback, private (RFC 1918, ULA `fc00::/7`), link-local (`169.254/16`, `fe80::/10`), CGNAT `100.64/10`, unspecified, multicast, reserved, broadcast, `0.0.0.0/8`, cloud metadata (`169.254.169.254`, `fd00:ec2::254`), IPv4-mapped/compatible IPv6 (`::ffff:127.0.0.1`), NAT64 `64:ff9b::/96` і 6to4 `2002::/16` з вбудованою забороненою IPv4, Docker-мережі (`backend`: `postgres`, `minio`, `mongo` резолвляться у 172.16/12 — блок через private). Числові форми хоста (decimal `2130706433`, octal `0177.0.0.1`, hex `0x7f.1`, скорочена `127.1`) канонізуються через `ipaddress`/`inet_aton`-семантику до перевірки. Trailing dot, `localhost`, `*.localhost` — блок за іменем.
4. **DNS pinning** — з'єднання відкривається **лише** з IP, який щойно пройшов перевірку (власний `httpcore.AsyncNetworkBackend`, SNI/`Host` — оригінальне ім'я); один резолв на hop, без повторного резолву бібліотекою; `trust_env=False` (проксі з env не обходять guard).
5. **Redirects** — вручну (`follow_redirects=False`), максимум 5 hop; кожен hop: Route Guard + SSRF + pinning; перехід на інший origin вимагає permit цього origin; origin без bucket → `redirect_origin_unknown` (permanent, без запиту); downgrade `https→http` — permanent `redirect_downgrade`.
6. **Ліміти body (§13)** — потокове читання з лічильником **розпакованих** байтів (gzip/deflate/brotli — `httpx[brotli]` або окремо `brotli`): >20 МБ (`COLLECTOR_FETCH_MAX_BODY_BYTES`) → обрив з'єднання, `body_too_large`, карантин; `Content-Length` > ліміту → відмова без читання body. `request_kind=sitemap`: ліміт 100 МБ **після** розпакування, зокрема для `.xml.gz`, що прийшов як `application/gzip` без `Content-Encoding` — інкрементальна перевірка через `zlib.decompressobj` з обмеженим `max_length`, raw bytes зберігаються стиснутими як отримано. Окремий ліміт стиснутого обсягу та ratio-guard проти bomb.
7. **Timeout (§10)** — connect 10 с, read 30 с, total 60 с на **весь** fetch (усі hop + body), override лише з manifest для sitemap.
8. **Conditional GET (FR-004)** — `If-None-Match`/`If-Modified-Since` з вхідних validators (O-7; `latest_validators` — WP-01A PR3a п.5, використовується з PR2); 304 → `FetchResult(not_modified=True)` без body.
9. **Класифікація і retry decisions (§10, §5.5)** — чиста функція `classify(response|error) -> FetchDecision(outcome, content_access, error_code, retry_after, route_incident)`: 2xx → `success`; 304 → `success`/not modified; 408/425/500/502/503/504, network, timeout → `retryable`; 429 → `retryable` + `block_origin`; 401/403 → `permanent_failure` + route incident (+ кандидат на browser fallback у PR2, лише якщо `browser_allowed`); 404/410 → `permanent_failure`, `content_access=gone`, **без** будь-якого `entity_lifecycle`; 200 з порожнім body → `retryable`/`empty_body`, **не** `gone` і не сигнал видалення (§11, FR-008); SSRF/guard → `permanent_failure`/`policy_blocked`. ### Тести (integration: PostgreSQL 18 + MinIO у Docker, loopback; HTTP — respx)

- **Crash між кроками (fault injection, §16.3):** (a) виняток після PUT до `commit_reference` → у PG немає reference, claim `leased`; об'єкт є в store; повторний handle (інший owner після expiry) — reacquire з `generation+1`, HEAD, commit успішний, рівно один `raw_objects`; (b) crash після acquire до PUT → sweeper після grace нічого не видаляє без reference-перевірки й не падає; (c) lease сплив між HEAD і commit → `StaleClaimError`, producer повторює claim **і** HEAD/reupload (перевірити кількість HEAD-викликів), stale generation не створює reference; (d) crash після commit до `queue.complete` → повторний handle: acquire бачить `committed`, PUT не виконується, `raw_objects` не дублюється, новий `fetches` рядок має новий `fetch_id`.
- **Sweeper vs producer:** producer тримає живий claim → `sweep_orphans` не видаляє об'єкт; sweeper узяв ключ → старий producer отримує `StaleClaimError` на commit, повторює PUT+HEAD після release sweeper-а; concurrent 2 producers одного `sha256` → рівно один reference, один PUT виконується.
- **Checksum:** store повертає інший sha256/size на HEAD (fake-corruption) → commit не виконується, retryable.
- **`storage.get` для споживачів:** об'єкт із sha256, відмінним від `expected_sha256`, або більший за `max_bytes` → помилка без повернення bytes; `FakeArtifactStore` проходить той самий набір контрактних тестів, що й MinIO-реалізація (параметризація по двох реалізаціях).
- **Дедуп:** ті самі bytes з двох URL → один об'єкт/один `raw_objects`, два `fetches` з одним `raw_sha256`.
- **D-2:** `put_normalized` з ключем, відмінним від `normalized/<entity_uuid>/<sha256>.json` → `ValueError`; ті самі bytes/сутність → той самий ключ; два fetch одного URL → два різні `fetch_id` у двох parse job; retry того самого parse job → той самий `fetch_id`; `fetch_id` у parse job == `fetches.fetch_id` у БД.
- **Preflight / pause ≤ 60 с (§16.3):** `set_source_state(paused)` після claim job → handler не робить запиту (respx 0 викликів), job не спалює спробу як помилку (`TaskResult.deferred`, WP-01D PR1c п.1: `attempt` не змінився); route `circuit_open` → 0 викликів.
- **403 → browser:** `browser_allowed=false` → route `circuit_open`, browser job не створено; `true` → рівно один `browser.render` при двох повторах handle (idempotency key); HTTP-результат записано окремим `fetches`.
- **429 end-to-end:** 429 → `block_origin` (audit-рядок є) + `TaskResult` retry з `not_before ≥ Retry-After`; другий handler на тому ж origin не робить запит до `blocked_until`.
- **304:** рядок `fetches` з `http_status=304`, `raw_sha256 IS NULL`, жодного claim/PUT/parse job.
- **Порожня відповідь ≠ видалення:** 200 з порожнім body і 404 → жодного `entity_lifecycle`/deletion-сигналу, жодного parse job з ознакою «видалено»; 404 → `content_access=gone` лише у `fetches`.
- **Robots:** два fetch з різним вмістом → два `raw_objects`; однаковий → один об'єкт, два `fetches`; TTL не минув → запиту немає; robots-запит бере permit (сумарний rate з page-запитами не перевищує bucket).
- **Ролі §13:** handler працює під LOGIN-роллю `collector_fetcher` (фікстури `tests/integration/postgres/test_role_logins.py` — зразок) — `record_fetch`, `record_raw_object`, claims, `block_origin`, `set_route_state`, `enqueue` проходять; спроба писати `normalized_artifacts`/`projection_tasks` під fetcher → permission denied.
- **Скінченний retry:** 5xx на всіх спробах → після 4-ї job у `quarantined` + dead letter (через runtime WP-01D і `max_attempts=4`).
- **Відсутність credentials у runtime (§16.3):** немає S3-секрету → `check_ready` падає, instance не `ready`, жодних спроб login до джерела; інші джерела (інший origin у тому ж процесі не зачеплено) — перевірити на рівні handler-а.

- Unit (Playwright замокано fake `Page`/`Route`): детектор — кожна fixture-сторінка challenge/CAPTCHA/login/paywall → `challenge`, route stop, **0** дій над сторінкою, **0** ретраїв; звичайна JS-сторінка → успіх; `browser_allowed=false` → браузер не запускається.
- Мережа браузера: subrequest на `http://169.254.169.254/`, `http://127.0.0.1/`, `ws://…`, `file://`, сторонній origin, redirect документа на private IP → `route.abort`, fake backend 0 connect; кожен дозволений subrequest бере permit.
- Ізоляція: два послідовні task-и — cookie/localStorage з першого відсутні в другому; context закрито навіть при винятку/cancel.
- Hostile HTML (§16.1 п.8): сторінка з нескінченним циклом JS/величезним DOM → timeout/ліміт, процес живий, permit звільнено.
- Integration/Docker (`-m integration`, loopback, без мережі до джерел): image збирається, запускається non-root, read-only rootfs; `docker compose --profile browser config` валідний; рендер локальної fixture-сторінки через `route.fulfill` (жодного зовнішнього запиту).
- R-16: для одного URL у БД два окремі `fetches` (HTTP 403 і browser) з різними `request_variant`.

## Rollback/disable

Схема БД не змінюється цим WP, тому revert PR безпечний; об'єкти в MinIO без reference прибирає sweeper після grace.
