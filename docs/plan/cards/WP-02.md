## Scope

Спільний fetch layer §7.1: нормалізація URL/origin (FR-014), Route Guard (allow/deny + глобальний denylist), SSRF-захищений HTTP-клієнт із DNS-pinning і перевіркою кожного redirect hop, потокові ліміти body (20 МБ / sitemap 100 МБ після розпакування), conditional GET, класифікація відповідей у `fetch_outcome`/`content_access` і скінченна retry policy §10, інтеграція з глобальним origin limiter (permit перед кожним запитом, 429/`Retry-After` → `block_origin`), claimed/verified PUT raw artifact-ів у S3/MinIO з `claim_generation` fencing і orphan sweeper (R-33/R-38/R-41), versioned robots snapshot, доменний `FetchHandler` для ролі `fetch` у runtime WP-01D, окремий browser worker image з pinned Playwright для винятків §3 п.11.

O-6 (WP-02 дає лише generic uploader і вимоги D-2); планування jobs і створення origin buckets (`ensure_bucket` — роль `collector_scheduler`) — WP-03/scheduler; `OriginPermitClient` як runtime-компонент — WP-01D PR2; виклик sweeper-а за розкладом, дашборди/алерти — WP-12; source manifests (`sources/<source_id>/manifest.yaml`) — адаптерні WP; live smoke будь-якого джерела — лише `source-canary` з дозволу користувача (у цьому WP не виконується).

## Відкрите для оркестратора

- **O-1 (`OriginPermitClient` до WP-01D PR2).** Рекомендація: PR1 оголошує тонкий Protocol `OriginPermits` у `collector/fetch/permits.py` (`acquire(origin, job_id) -> Permit | Denied(reason, retry_after)`, `release(permit)`, `block(origin, until, reason)`), а HTTP-клієнт залежить лише від нього; тимчасовий адаптер `PgOriginPermits` прямо викликає `limiter.acquire_permit/release_permit(owner_instance=…)/block_origin` WP-01A (окремі короткі транзакції, як вимагають docstrings). PR1 може йти паралельно з WP-01D PR2. PR2 (прив'язка до runtime) бажано зливати **після** WP-01D PR2 і використовувати `OriginPermitClient`; якщо WP-01D PR2 не встигає — лишається адаптер + тест-вартовий: падає, щойно `collector.core.limiter_runtime.OriginPermitClient` імпортується, вимагаючи видалити `PgOriginPermits`. Альтернатива — жорсткий порядок WP-01D PR2 → WP-02 PR1. Рішення за оркестратором.
- **O-2 (Scrapy vs HTTPX, конфлікт із §8).** §8 називає Scrapy 2.13 «основним HTTP crawler», а `FORBIDDEN_FOUNDATION_DEPS` його забороняє. Картка передбачає `httpx` (async у тому самому event loop, що `WorkerRuntime`; власний `httpcore` network backend для DNS-pinning; `trust_env=False`), бо Twisted-реактор Scrapy не вбудовується в asyncio-runtime WP-01D і не дає hop-level контролю SSRF. Це відхилення від §8 → ADR у PR1 + правка ТЗ §8 через пострев'ю (ескалація типу (б) §11 плану). Потрібне підтвердження до старту PR1.
- **O-3 (S3-клієнт).** Залежності для S3 у проєкті немає. Пропозиція: `aiobotocore` (async, сумісний із managed S3 у prod) + dev `types-aiobotocore-s3` для mypy strict. Альтернатива — `minio` (sync, через `asyncio.to_thread`). Вибір — ADR у PR2.
- **O-4 (Route Guard і denylist без перевипуску, §3 п.10).** У PostgreSQL немає таблиці allow/deny patterns чи denylist; manifests адаптерів ще не існують. Пропозиція PR1: `RouteGuard` споживає `allow/deny` patterns як дані (з manifest через `manifest_uri` — пізніше) і глобальний denylist з файлу, змонтованого через Docker config/secret і перечитуваного за mtime; довгострокове — таблиця WP-01A. Рішення — оркестратор.
- **O-5 (browser: DNS-rebinding і subrequests).** Chromium резолвить DNS сам, `page.route` не дає pinning. Пропозиція PR3: кожен дозволений request браузера виконується через SSRF-захищений клієнт PR1 і повертається `route.fulfill` (permit на кожен запит до лімітованого origin), сторонні origins заблоковані за замовчуванням (allowlist з manifest), типи `image/media/font` блокуються (Q-002). Ціна — повільніший рендер; альтернатива — локальний SSRF-proxy. Рішення — оркестратор + security review.
- **O-6 (owner parse worker handler).** Dependency `WP-01A-to-WP-02.md` адресований «fetch/parse workers», але §17.2 дає WP-02 лише fetch, а parser — адаптерам/WP-05. Пропозиція: WP-02 PR2 закриває умови D-2 у тій частині, якою володіє (ключ normalized object, справжній `fetch_id` у parse job), і дає generic `ArtifactUploader.put_normalized`; handler ролі `parse` і умову 3 (`parser_version` при зміні схеми) переносять у картку його owner-а (WP-05 або окремий WP). Статус deps-файла після PR2 — `partially resolved`.
- **O-7 (304 і freshness).** `collector_fetcher` має лише `INSERT` на `fetches`, тому 304 фіксується новим рядком `fetches` (`http_status=304`, `outcome=success`, `raw_sha256=NULL`), без нового raw object і без parse job; «freshness» виводиться з цих рядків. Підтвердити, що окремої колонки/таблиці freshness не треба.

## Спільні вимоги для всіх PR

- **Мережа в тестах — лише mock.** HTTP-семантика — `respx` (є в dev-залежностях); DNS — інʼєктований `Resolver` (fake); TCP connect — fake `httpcore.AsyncNetworkBackend`, що записує `(ip, port)`. Жодного live-запиту, жодного реального DNS: у `tests/unit/fetch/conftest.py` autouse-фікстура підміняє `socket.getaddrinfo`/`loop.getaddrinfo` на функцію, що кидає, бо pytest-socket не перехоплює `getaddrinfo` (докстрінг `tests/conftest.py`). Loopback — лише integration для PostgreSQL/MinIO.
- **Linux-паритет.** На Linux `--disable-socket` блокує навіть loopback у unit-тестах, на Windows — ні (HANDOFF §6). Реалізатор проганяє `tests/unit/fetch` також у Linux-контейнері (`docker run … uv run pytest tests/unit/fetch`) і вставляє вивід у `implementation.md`; тест, що потребує сокета, не має маркера `unit`.
- **Тест проти мовчазного skip.** `tests/integration/fetch/conftest.py` за зразком `tests/integration/postgres/conftest.py`: Docker/MinIO недоступні + `COLLECTOR_TEST_REQUIRE_DOCKER=1` → fail, не skip. Плюс `tests/integration/fetch/test_suite_is_enforced.py` (зразок — `tests/e2e/test_runtime_suite_is_enforced.py`): під прапорцем кожен модуль suite має реально виконатись (0 skipped). Tester доводить, що без MinIO job падає.
- **Кожен тест має падати на зламаній реалізації** (§7 плану): для SSRF/limits/claim tester мутує guard (напр. прибирає перевірку hop-у) і показує червоний прогін у `testing.md`.
- Стабільний `User-Agent` із конфігу (`COLLECTOR_FETCH_USER_AGENT`, містить назву й версію, §3 п.5); жодних cookies між запитами (no cookie jar), жодних `Authorization`/API keys; URL з userinfo (`http://u:p@host`) відхиляється (`url_userinfo_forbidden`) — v1 anonymous-only (Q-007).

- Handler не блокує event loop: розпакування/хешування великих body — інкрементально або `asyncio.to_thread` (контракт `docs/workers.md` §5); коректна реакція на `CancelledError` — permit і claim звільняються у `finally`.

## PR1 — `wp/02-1-http-ssrf-limits`: URL/origin, Route Guard, SSRF-клієнт, ліміти, retry decisions, permits

### Вимоги

1. **URL (FR-014)** — `collector/fetch/urls.py`: `normalize_url(raw) -> NormalizedUrl` (lowercase scheme/host, IDNA, прибрати default port, fragment і tracking-параметри за `tracking_query_keys`; вихідний рядок зберігається) і `normalize_origin(url) -> str` (`scheme://host[:port]`) — **єдиний** ключ `origin_rate_buckets.origin`; WP-03/scheduler імпортують саме цю функцію.
2. **Route Guard** — лише `http`/`https`; дозволені порти за замовчуванням 80/443 (override з policy); allow/deny patterns + глобальний denylist (O-4); перевірка до кожного запиту і на кожному hop.
3. **SSRF (§13)** — `collector/fetch/ssrf.py`: резолв **усіх** A/AAAA; блок, якщо **хоча б одна** адреса не глобальна: loopback, private (RFC 1918, ULA `fc00::/7`), link-local (`169.254/16`, `fe80::/10`), CGNAT `100.64/10`, unspecified, multicast, reserved, broadcast, `0.0.0.0/8`, cloud metadata (`169.254.169.254`, `fd00:ec2::254`), IPv4-mapped/compatible IPv6 (`::ffff:127.0.0.1`), NAT64 `64:ff9b::/96` і 6to4 `2002::/16` з вбудованою забороненою IPv4, Docker-мережі (`backend`: `postgres`, `minio`, `mongo` резолвляться у 172.16/12 — блок через private). Числові форми хоста (decimal `2130706433`, octal `0177.0.0.1`, hex `0x7f.1`, скорочена `127.1`) канонізуються через `ipaddress`/`inet_aton`-семантику до перевірки. Trailing dot, `localhost`, `*.localhost` — блок за іменем.
4. **DNS pinning** — з'єднання відкривається **лише** з IP, який щойно пройшов перевірку (власний `httpcore.AsyncNetworkBackend`, SNI/`Host` — оригінальне ім'я); один резолв на hop, без повторного резолву бібліотекою; `trust_env=False` (проксі з env не обходять guard).
5. **Redirects** — вручну (`follow_redirects=False`), максимум 5 hop; кожен hop: Route Guard + SSRF + pinning; перехід на інший origin вимагає permit цього origin; origin без bucket → `redirect_origin_unknown` (permanent, без запиту); downgrade `https→http` — permanent `redirect_downgrade`.
6. **Ліміти body (§13)** — потокове читання з лічильником **розпакованих** байтів (gzip/deflate/brotli — `httpx[brotli]` або окремо `brotli`): >20 МБ (`COLLECTOR_FETCH_MAX_BODY_BYTES`) → обрив з'єднання, `body_too_large`, карантин; `Content-Length` > ліміту → відмова без читання body. `request_kind=sitemap`: ліміт 100 МБ **після** розпакування, зокрема для `.xml.gz`, що прийшов як `application/gzip` без `Content-Encoding` — інкрементальна перевірка через `zlib.decompressobj` з обмеженим `max_length`, raw bytes зберігаються стиснутими як отримано. Окремий ліміт стиснутого обсягу та ratio-guard проти bomb.
7. **Timeout (§10)** — connect 10 с, read 30 с, total 60 с на **весь** fetch (усі hop + body), override лише з manifest для sitemap.
8. **Conditional GET (FR-004)** — `If-None-Match`/`If-Modified-Since` з вхідних validators (O-7, deps WP-01A п.2); 304 → `FetchResult(not_modified=True)` без body.
9. **Класифікація і retry decisions (§10, §5.5)** — чиста функція `classify(response|error) -> FetchDecision(outcome, content_access, error_code, retry_after, route_incident)`: 2xx → `success`; 304 → `success`/not modified; 408/425/500/502/503/504, network, timeout → `retryable`; 429 → `retryable` + `block_origin`; 401/403 → `permanent_failure` + route incident (+ кандидат на browser fallback у PR2, лише якщо `browser_allowed`); 404/410 → `permanent_failure`, `content_access=gone`, **без** будь-якого `entity_lifecycle`; 200 з порожнім body → `retryable`/`empty_body`, **не** `gone` і не сигнал видалення (§11, FR-008); SSRF/guard → `permanent_failure`/`policy_blocked`. Retry policy скінченна: `max_attempts=4`, backoff 5 с/30 с/2 хв/10 хв + jitter (виконання в черзі — deps WP-01A п.5, WP-01D п.1).
10. **429/`Retry-After`** — секунди або HTTP-date; відсутній/сміттєвий/від'ємний → default (10 хв); clamp `[5 с, 24 год]`; `permits.block(origin, until)` → `limiter.block_origin` (audit там же, `actor=worker_instance_id`, `reason="http_429"`).

## PR2 — `wp/02-2-raw-upload-claim`: artifact store, claimed/verified PUT, robots snapshot, `FetchHandler`, sweeper

### Вимоги

1. **Artifact store** — `collector/fetch/store.py`: async S3-клієнт (O-3), bucket/endpoint з `COLLECTOR_MINIO_URL` + секрет із файлу; операції `put(key, bytes, sha256, media_type)`, `head(key) -> (size, sha256|etag)`, `delete(key)` (лише sweeper). Checksum перевіряється власним `x-amz-meta-sha256`/`ChecksumSHA256`, а не ETag (multipart ETag ≠ md5).
2. **Claimed/verified PUT (§10 п.5, R-33/R-38/R-41)** — `collector/fetch/upload.py`, generic для raw і normalized:
   1. `acquire_upload_claim(key, owner=worker_instance_id, lease_seconds)` — окрема коротка транзакція;
   2. PUT → HEAD/size/sha256 verification поза транзакцією;
   3. `commit_reference(key, generation, owner, sha256, size, uri)` + `record_raw_object` **в одній** транзакції;
   4. `StaleClaimError` на commit (lease сплив або reacquire) → повтор з кроку 1 **з HEAD/reupload**, максимум N разів, далі retryable;
   5. `StaleClaimError` на acquire через `committed` — **ті самі bytes уже збережені** (content-addressed): upload пропускається, береться наявний `raw_objects` рядок (дедуп, `raw_dedup_ratio`);
   6. живий claim іншого producer-а → коротке очікування/retryable, **не** паралельний PUT.
3. **Ключі (§9.3 п.4 + D-2 умова 1)** — raw: `raw/<sha256>`; normalized: `normalized_object_key(entity_uuid, sha256) = "normalized/<entity_uuid>/<sha256>.json"` — єдина функція; `put_normalized(ref: NormalizedArtifactRef, body)` сам виводить ключ і відхиляє будь-який інший.
4. **`fetch_id` (D-2 умова 2)** — кожен HTTP-запит (зокрема 304, помилки, кожна спроба ретраю) → **новий** рядок `fetches` через `record_fetch`; `RawArtifactRef.fetch_id` і `fetch_id` у args parse job — саме `Fetch.fetch_id` з цього рядка; повтор parse job (retry/replay) несе той самий `fetch_id`, новий fetch того самого URL — новий. Parse job enqueue з ідемпотентним ключем від `fetch_id` (повторний handle після crash не дублює job).
5. **D-2 умова 3** — зміна схеми target collection = зміна `parser_version`: у README fetch layer і docstring `put_normalized`; виконання — owner parse handler-а (O-6).
6. **Robots snapshot (§3 п.3, §10 п.2)** — `collector/fetch/robots.py`: `/robots.txt` origin-а отримується тим самим SSRF-клієнтом під permit (`request_kind=robots`), зберігається як raw artifact (versioned = новий `sha256` → новий `raw_objects`, історія — рядки `fetches`); не частіше за `COLLECTOR_ROBOTS_TTL` (default 24 год); 404 → snapshot «відсутній» (фіксується fetch-рядком), 5xx → попередній snapshot. Поведінка за `policy.robots_policy` (діагностика за замовчуванням, §3 п.3); значення, що вимагає блоку, → `policy_blocked` із посиланням на snapshot.
7. **`FetchHandler`** — `collector/fetch/handler.py`, `job_types = ("fetch.http",)`, реєстрація `HANDLER_FACTORIES[WorkerRole.FETCH]`; кроки: preflight (source `enabled`, route не `circuit_open`, URL проходить Route Guard — повторна перевірка policy перед запитом, §10 п.4) → permit → fetch (PR1) → для 200/206 upload claim protocol + `record_fetch(raw_sha256=…)`; 304 → `record_fetch` без raw (O-7); 401/403/challenge → `set_route_state(circuit_open, actor, reason)` + (якщо `browser_allowed` і route kind дозволяє) enqueue `browser.render` з `request_variant="browser"` рівно раз на URL; результати HTTP і browser — окремі рядки `fetches` (R-16). Повертає `TaskResult` за класифікацією PR1; `check_ready` — HEAD bucket + `SELECT 1`.
8. **Orphan sweeper** — `collector/fetch/sweeper.py::sweep_orphans(grace)`: `list_orphan_candidates(grace)` + **обов'язковий fencing-протокол** з docstring (acquire як sweeper → delete → `release_claim`); `grace` > максимального вікна PUT+HEAD+commit (конфіг-перевірка). Виклик за розкладом — WP-12 (maintenance), облікові дані з `DeleteObject` — лише maintenance (deps WP-00 п.3).
9. Метрики-лічильники в коді (`http_requests_total{source,status_class}`, `http_429_total`, `policy_blocks_total`, `raw_bytes_total`, `raw_dedup_ratio`, `artifact_orphans_total`); експорт — WP-12.

### Тести (integration: PostgreSQL 18 + MinIO у Docker, loopback; HTTP — respx)

- **Crash між кроками (fault injection, §16.3):** (a) виняток після PUT до `commit_reference` → у PG немає reference, claim `leased`; об'єкт є в store; повторний handle (інший owner після expiry) — reacquire з `generation+1`, HEAD, commit успішний, рівно один `raw_objects`; (b) crash після acquire до PUT → sweeper після grace нічого не видаляє без reference-перевірки й не падає; (c) lease сплив між HEAD і commit → `StaleClaimError`, producer повторює claim **і** HEAD/reupload (перевірити кількість HEAD-викликів), stale generation не створює reference; (d) crash після commit до `queue.complete` → повторний handle: acquire бачить `committed`, PUT не виконується, `raw_objects` не дублюється, новий `fetches` рядок має новий `fetch_id`.
- **Sweeper vs producer:** producer тримає живий claim → `sweep_orphans` не видаляє об'єкт; sweeper узяв ключ → старий producer отримує `StaleClaimError` на commit, повторює PUT+HEAD після release sweeper-а; concurrent 2 producers одного `sha256` → рівно один reference, один PUT виконується.
- **Checksum:** store повертає інший sha256/size на HEAD (fake-corruption) → commit не виконується, retryable.
- **Дедуп:** ті самі bytes з двох URL → один об'єкт/один `raw_objects`, два `fetches` з одним `raw_sha256`.
- **D-2:** `put_normalized` з ключем, відмінним від `normalized/<entity_uuid>/<sha256>.json` → `ValueError`; ті самі bytes/сутність → той самий ключ; два fetch одного URL → два різні `fetch_id` у двох parse job; retry того самого parse job → той самий `fetch_id`; `fetch_id` у parse job == `fetches.fetch_id` у БД.
- **Preflight / pause ≤ 60 с (§16.3):** `set_source_state(paused)` після claim job → handler не робить запиту (respx 0 викликів), job не спалює спробу як помилку (disposition за deps WP-01D п.2); route `circuit_open` → 0 викликів.
- **403 → browser:** `browser_allowed=false` → route `circuit_open`, browser job не створено; `true` → рівно один `browser.render` при двох повторах handle (idempotency key); HTTP-результат записано окремим `fetches`.
- **429 end-to-end:** 429 → `block_origin` (audit-рядок є) + `TaskResult` retry з `not_before ≥ Retry-After`; другий handler на тому ж origin не робить запит до `blocked_until`.
- **304:** рядок `fetches` з `http_status=304`, `raw_sha256 IS NULL`, жодного claim/PUT/parse job.
- **Порожня відповідь ≠ видалення:** 200 з порожнім body і 404 → жодного `entity_lifecycle`/deletion-сигналу, жодного parse job з ознакою «видалено»; 404 → `content_access=gone` лише у `fetches`.
- **Robots:** два fetch з різним вмістом → два `raw_objects`; однаковий → один об'єкт, два `fetches`; TTL не минув → запиту немає; robots-запит бере permit (сумарний rate з page-запитами не перевищує bucket).
- **Ролі §13:** handler працює під LOGIN-роллю `collector_fetcher` (фікстури `tests/integration/postgres/test_role_logins.py` — зразок) — `record_fetch`, `record_raw_object`, claims, `block_origin`, `set_route_state`, `enqueue` проходять; спроба писати `normalized_artifacts`/`projection_tasks` під fetcher → permission denied.
- **Скінченний retry:** 5xx на всіх спробах → після 4-ї job у `quarantined` + dead letter (через runtime WP-01D і `max_attempts=4`).
- **Відсутність credentials у runtime (§16.3):** немає S3-секрету → `check_ready` падає, instance не `ready`, жодних спроб login до джерела; інші джерела (інший origin у тому ж процесі не зачеплено) — перевірити на рівні handler-а.

### Acceptance PR2

## Rollback/disable

`fetch-worker` без зареєстрованого handler-а повертається до `NoopHandler` (прибрати імпорт реєстрації або `COLLECTOR_WORKER_PLACEHOLDER=1`, `docs/workers.md`); масштаб `--scale fetch-worker=0`; зупинка конкретного джерела — `sources.set_source_state(paused)` (preflight перевіряє перед кожним запитом), конкретного route — `circuit_open`, конкретного origin — `block_origin`; глобальний denylist (O-4); browser — profile `browser` не вмикається, replicas 0 (default). Схема БД не змінюється цим WP, тому revert PR безпечний; об'єкти в MinIO без reference прибирає sweeper після grace.
