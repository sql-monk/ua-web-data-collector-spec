## Scope

Створити відтворюваний каркас репозиторію, у якому всі наступні WP працюють незалежно: Python-проєкт із lockfile, CLI-контракт §16.2, тестова інфраструктура з забороною мережі, lint/type/secret-scan, CI, Docker images та Compose profiles, web scaffold.

## Out of scope

Будь-яка доменна логіка: контракти (WP-01C), міграції (WP-01A), Mongo validators (WP-01B), fetch/discovery/translation, адаптери, реальні API endpoints (WP-11A), екрани GUI (WP-11C), observability stack наповнення (WP-12). Стаби, які WP-00 створює для health/migrate/ensure-mongo, явно позначаються як стаби і замінюються власниками.

## Спільні правила для всіх під-PR

- Owned files — лише перелічені в під-PR. Forbidden: `docs/research/**`, `TECHNICAL_SPECIFICATION.md` (крім одноразової правки назв CLI у §16.2, якщо фінальні назви відрізняються — це єдина дозволена зміна ТЗ, §16.2), `REVIEW.md`.
- Версії залежностей pinned через `uv.lock`/`package-lock.json`; Docker images — tag + digest.
- Українська мова у README/коментарях користувацького рівня; ідентифікатори — англійською.
- Наступні WP додають свої залежності у `pyproject.toml` самостійно (алфавітний порядок у списку, щоб мінімізувати конфлікти) і перегенеровують `uv.lock`; WP-00 фіксує лише foundation-залежності.

## PR2 — `wp/00-2-docker-compose`: images + Compose profiles

### Owned files

`Dockerfile`, `deploy/compose/**`, `docker-compose.yml`, `.dockerignore`, `src/collector/api/health.py` (стаб health — далі owner WP-11A), `src/collector/cli.py` (лише команди `api`/`db migrate`/`db ensure-mongo` стаби → мінімальна реальна поведінка для health), `.github/workflows/ci.yml` (додати compose/build кроки), `docs/decisions/0002-docker-compose-single-host.md`.

**Фактичний scope PR2 (фіксація пострев'ю `spec-review-pr2.md`, знахідка F-4, 2026-09-22):**
список вище доповнено файлами, необхідними для вимог 1–9 і Docs PR2, які виявились поза
початковим списком: `tests/**` (нові unit/integration тести на compose/health/CLI — вимога
«докази у звітах»), `pyproject.toml`, `uv.lock` (нові runtime-залежності `fastapi`, `uvicorn`,
`pymongo` для health-стаба), `.gitignore` (реальні файли `deploy/compose/secrets/*`),
`.gitattributes` (`*.sh text eol=lf` — без цього Windows `core.autocrlf` ламає
`init-secrets.sh` у Linux-контейнері/CI), `docs/runbooks/**` (`clean-host-start.md`,
`rollback-image.md`). Forbidden-файли (`docs/research/**`, `TECHNICAL_SPECIFICATION.md`,
`REVIEW.md`) не змінювались — перевірено пострев'ю.

### Вимоги (§7.5, §13)

1. Один multi-stage image `collector` (uv builder → runtime `python:3.13-slim@sha256:…`), non-root user, read-only rootfs + tmpfs `/tmp`, OCI labels (Git SHA, schema version), `HEALTHCHECK`. Browser image — не тут (WP-02 PR3).
2. `docker-compose.yml` з profiles `core`, `workers`, `browser`, `gui`, `observability`, `tools`; сервіси за таблицею §7.5; workers без `container_name`, без host ports, без local persistent state; `deploy.resources.limits` для всіх; `stop_grace_period` ≥ 90 с для workers.
3. Мережі `ingress`, `backend`, `source-egress`, `provider-egress`, `telemetry` за §7.5; discovery/fetch/browser у `source-egress`, translation у `provider-egress`, api — `backend` + `ingress`, gui бачить лише api.
4. Stateful: `postgres` (PostgreSQL 18, pinned digest), `mongo` (MongoDB 8.0 replica set single-member, pinned digest, keyfile/секрети), `minio` (pinned digest) — named volumes; ports не публікуються назовні (за замовчуванням лише `127.0.0.1` binding через override-файл `deploy/compose/dev.override.yml` для локальної розробки).
5. One-shot `migrate-postgres` (`collector db migrate` — стаб, що перевіряє з'єднання і завершується 0 із повідомленням «no migrations yet; owner WP-01A»), `ensure-mongo` (ініціалізує single-member replica set, якщо не ініціалізовано; validators/indexes — стаб для WP-01B). `api` — мінімальний FastAPI-стаб лише з `GET /api/v1/health/components`, readiness `false`, доки не завершені one-shots (через `depends_on: condition: service_completed_successfully`).
6. Secrets через Docker secrets/files у `deploy/compose/secrets/*.example`; реальні файли в `.gitignore`; жодного секрету в image layer або `ARG`.
7. Healthcheck кожного сервісу перевіряє process + критичну dependency; `scheduler` — singleton (стаб-процес, що бере advisory lease — реалізація WP-01D; тут лише placeholder-команда `collector scheduler`, що тримає процес живим і логує, що lease-логіка ще не реалізована).
8. Документована команда clean-host start: `docker compose --profile core --profile workers --profile gui up -d --wait` — у PR2 profile `gui` може бути відсутнім до PR3; тоді acceptance виконується для `core` + `workers`, а `gui` додається у PR3.
9. CI: `docker compose config --quiet`, `docker build` image `collector`, SBOM (`syft` або `docker sbom`, якщо доступно; інакше — зафіксувати як `operationally unverified` у звіті), vulnerability scan (`trivy`, якщо доступний).

### Команди перевірки

```bash
docker compose config --quiet
docker compose build --pull
docker compose --profile core --profile workers up -d --wait
docker compose ps
docker compose down -v
uv run pytest -m "not live"
```

### Acceptance (§16.3, R-51, R-55)

- чистий host піднімає `core` + `workers` однією командою; всі сервіси `healthy`; workers — стаби, які живі й не падають;
- restart (`docker compose restart`) не втрачає дані named volumes (перевірити маркерним записом у postgres/minio);
- `docker compose config` не містить `container_name` для workers, не містить Docker socket mount у жодному сервісі, не містить public port крім `gui`/dev-override;
- images non-root (перевірити `docker inspect` → `Config.User`), read-only rootfs у compose;
- жоден secret не потрапив у image (`docker history`, `docker run --rm collector env`).

## PR4 — `wp/00-4-role-dsn-secrets`: per-component DSN secrets, `db roles --with-login`, REVOKE PUBLIC

Закриває `docs/plan/deps/WP-01A-to-WP-00.md` §4 і §6 (частина блокера pilot §13, разом з WP-01D PR1b). Worktree `.worktrees/wp-00-4`. Паралельно з WP-01D PR1b (`wp/01d-1b-runtime-role-dsn`).

### Owned files

`deploy/compose/secrets/**` (`init-secrets.sh`, нові `postgres_dsn_<component>.example`), `deploy/compose/postgres/init/**`, `docker-compose.yml` — **лише** top-level `secrets:` і сервіс `migrate-postgres`; `.github/workflows/**` (якщо CI генерує секрети інакше, ніж через `init-secrets.sh`), `tests/unit/test_compose_config*.py` і `tests/unit/test_secrets*.py` — лише тести на owned-частину, `deploy/compose/README.md`, `docs/runbooks/clean-host-start.md`, `docs/plan/reports/WP-00/*-pr4.md`.

Forbidden: `x-worker`, `scheduler`, `*-worker` сервіси в `docker-compose.yml` (WP-01D PR1b), `src/**`, `sql/**`, `migrations/**`, тест-вартовий `test_runtime_dsn_is_a_temporary_deviation_from_13_with_a_tripwire` (WP-01D).

### Вимоги

1. `init-secrets.sh` генерує сім секретів `postgres_dsn_<component>` для `scheduler`, `fetcher`, `parser`, `projector`, `translation`, `api_ro`, `export_ro` у форматі `postgresql://collector_<component>:<random_hex_48>@${POSTGRES_HOST:-postgres}:${POSTGRES_PORT:-5432}/${POSTGRES_DB:-collector}`, **кожен зі своїм** паролем (hex, printable ASCII). Ідемпотентно, як і наявні секрети: існуючий файл не перезаписується. Поруч `postgres_dsn_<component>.example` із плейсхолдером без секрету.
2. Top-level `secrets:` у `docker-compose.yml` отримує сім записів, дослівно в такому вигляді й одразу після `postgres_dsn` (щоб паралельна гілка WP-01D PR1b дала ідентичний hunk):

   ```yaml
     # Per-component LOGIN-ролі §13 (WP-01A PR2 `db roles --with-login`): кожен runtime-сервіс
     # монтує лише свій DSN; `migrate-postgres` монтує всі, щоб виставити паролі ролям.
     postgres_dsn_scheduler:
       file: ./deploy/compose/secrets/postgres_dsn_scheduler
     postgres_dsn_fetcher:
       file: ./deploy/compose/secrets/postgres_dsn_fetcher
     postgres_dsn_parser:
       file: ./deploy/compose/secrets/postgres_dsn_parser
     postgres_dsn_projector:
       file: ./deploy/compose/secrets/postgres_dsn_projector
     postgres_dsn_translation:
       file: ./deploy/compose/secrets/postgres_dsn_translation
     postgres_dsn_api_ro:
       file: ./deploy/compose/secrets/postgres_dsn_api_ro
     postgres_dsn_export_ro:
       file: ./deploy/compose/secrets/postgres_dsn_export_ro
   ```

3. One-shot `migrate-postgres`: `collector db migrate && collector db roles --with-login` (через `sh -c` або еквівалент, без втрати exit code), монтує `postgres_dsn` і всі сім `postgres_dsn_<component>`; каталог секретів `/run/secrets` (типовий для `COLLECTOR_POSTGRES_ROLE_SECRETS_DIR`). Повторний запуск (restart stack) ідемпотентний.
4. `deploy/compose/postgres/init/**`: при першому старті кластера `REVOKE CONNECT, TEMP ON DATABASE collector FROM PUBLIC` і явний `GRANT CONNECT` group-ролям §13, яким він потрібен; `REVOKE ALL ON DATABASE postgres, template1 FROM PUBLIC` там, де це безпечно для healthcheck/one-shots (обґрунтувати у звіті). Наявний вартовий «в init немає GRANT на таблиці/паролів» лишається зеленим (GRANT CONNECT на БД — не GRANT на таблиці; якщо вартовий цього не розрізняє — уточнити його, не послабивши).
5. CI job `docker` (clean-host `up --wait` + e2e) зелений: секрети генеруються тим самим шляхом, що й локально.

### Тести

Unit на compose-конфіг: `migrate-postgres` монтує рівно `postgres_dsn` + сім per-role, команда містить `--with-login`; кожен per-role секрет оголошено; `init-secrets.sh` генерує вісім DSN із попарно різними паролями й користувачем = роль (запуск скрипту в tmp-каталозі, без мережі); `.example` без справжніх секретів. Integration/Docker: після `up --wait` під `collector_fetcher` DSN можна підключитися, а до БД `postgres` — ні (або обґрунтований `not testable offline`).

### Команди перевірки

Як у PR2, плюс `docker compose --profile core --profile workers up -d --wait` на чистому хості (після `init-secrets.sh`) і `docker compose down -v`.

### Acceptance

`migrate-postgres` завершується 0 і дає сім LOGIN-ролей; повторний `up` ідемпотентний; жоден пароль не потрапляє в `environment`/`docker inspect`/логи; §13 «REVOKE PUBLIC» виконано для БД `collector`.

### Вимоги

1. **MinIO buckets і per-role облікові дані (§13 «writer/parser/auditor roles»).** One-shot
   `ensure-minio` (vendor `mc`, pinned digest; `depends_on: minio: service_healthy`) ідемпотентно
   створює buckets `raw`, `normalized`, `archive`, `translated`, `events` (імена ключів у bucket-і
   — конвенція WP-02 `collector.storage`) і користувачів/policies:

   | Компонент | Секрет | Дозволи |
   |---|---|---|
   | fetcher (`fetch-`, `browser-`, `discovery-worker`) | `minio_fetcher` | `raw`: Put/Get/Head, **без** Delete |
   | parser (`parse-worker`) | `minio_parser` | `raw`: Get/Head; `normalized`: Put/Get/Head |
   | projector (`projector-worker`: projector, reconciler, compactor) | `minio_projector` | `normalized`: Get/Head; `events`, `archive`: Put/Get/Head; Delete — лише `archive` (sweep після rollback window, WP-01B PR4) |
   | translation (`translation-worker`) | `minio_translation` | `normalized`: Get/Head; `translated`: Put/Get/Head |
   | maintenance (`maintenance-worker`, sweeper WP-02/WP-12) | `minio_maintenance` | `raw`, `normalized`, `events`, `translated`: List/Head/Delete |
   | api/export (`api`, `export-worker`) | `minio_readonly` | усі buckets: Get/Head |

   Root-облікові дані MinIO монтує лише `ensure-minio`. Формат секрету — файл з access key і
   secret key (або два файли; обрати й зафіксувати в `deploy/compose/README.md`), генерація в
   `init-secrets.sh` (випадкові, printable ASCII, ідемпотентно — наявний файл не
   перезаписується), `.example` без секрету.
2. **Mongo per-component URI (§13, WP-01B PR1 п.6).** `init-secrets.sh` генерує
   `mongo_uri_projector`, `mongo_uri_compactor`, `mongo_uri_api_ro`, `mongo_uri_export_ro`
   (кожен зі своїм паролем, `replicaSet=rs0`, `authSource=admin`); one-shot `ensure-mongo`
   виконує `collector db ensure-mongo --validators --indexes --users` (прапорець `--users` —
   прийняте припущення WP-01B, реалізація CLI — WP-01B PR1; до її merge команда лишається
   як зараз, а PR5 додає прапорці за feature-перемикачем у compose або одночасно з WP-01B PR1 —
   хто зливається другим, робить rebase); scheduler, fetch/discovery/browser/parse-worker
   Mongo-секретів **не** монтують (тест-вартовий).
3. **Секрет провайдера перекладу (WP-04).** `google_translation_credentials`: `.example`-заглушка;
   `init-secrets.sh` **не генерує** значення (зовнішній credential оператора), але створює
   **порожній** файл, якщо його немає (інакше `docker compose up` падає на відсутньому
   file-secret); top-level `secrets:`; монтує лише `translation-worker`; env
   `COLLECTOR_TRANSLATION_PROVIDER=disabled` (default), `COLLECTOR_TRANSLATION_PROJECT`,
   `COLLECTOR_TRANSLATION_LOCATION`, `COLLECTOR_TRANSLATION_CREDENTIALS_FILE=/run/secrets/
   google_translation_credentials`. Gitleaks без allowlist-винятків під нього.
4. **Монтування у сервіси:** кожен сервіс монтує лише свої MinIO/Mongo/provider-секрети за
   таблицею п.1–3 (`COLLECTOR_MINIO_CREDENTIALS_FILE`, `COLLECTOR_MONGO_URI_FILE`);
   `projector-worker` отримує `depends_on: ensure-mongo` (completed) і `ensure-minio`
   (completed).
5. CI job `docker` (clean-host `up --wait` + e2e) зелений: секрети генеруються тим самим
   шляхом, що й локально.

### Тести

Unit на compose-конфіг: кожен runtime-сервіс монтує рівно свої MinIO/Mongo-секрети за
таблицею, root MinIO — лише `ensure-minio`, root Mongo — лише `ensure-mongo`; scheduler/fetcher/
parser не мають Mongo-секретів; `google_translation_credentials` монтує лише
`translation-worker`; `init-secrets.sh` у tmp-каталозі генерує всі нові секрети з попарно
різними паролями, не перезаписує наявні і створює порожній
`google_translation_credentials`; `.example` без справжніх секретів. Integration/Docker: після
`up --wait` облікові дані `minio_fetcher` не можуть `DeleteObject` у `raw` і `PutObject` у
`normalized`; `minio_maintenance` може `DeleteObject`; `mongo_uri_api_ro` не може insert
(або обґрунтований `not testable offline` з датою).

### Команди перевірки

Як у PR2, плюс `deploy/compose/secrets/init-secrets.sh` на чистому каталозі,
`docker compose --profile core --profile workers up -d --wait` і `docker compose down -v`.

### Acceptance

`ensure-minio` і `ensure-mongo` завершуються 0 і ідемпотентні при повторному `up`; жоден
пароль не потрапляє в `environment`/`docker inspect`/логи; §13 «облікові дані за компонентами»
виконано для MinIO і Mongo; `docker compose config --quiet` зелений.
